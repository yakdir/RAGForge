# ADR-003: 文档分块策略 — 递归分块 512/64

## 状态

已采纳

## 背景

RAG 系统需要把长文档切成小块（chunk），才能做向量化和检索。分块策略直接影响检索效果：

- 块太大：一个 chunk 里混了多个主题，检索不精准
- 块太小：上下文不完整，答案不连贯

常见的分块策略：

- **固定长度分块**：按固定字符数切，简单粗暴
- **递归分块**：按段落 → 句子 → 词的层级递归切，尽量保留语义完整性
- **语义分块**：用 embedding 相似度判断哪里该切，效果好但慢

## 决策

选择 **递归分块**，chunk_size=512 字符，overlap=64 字符。

## 理由

1. **保留语义完整性**
   - 递归分块先按段落切，段落太长再按句子切
   - 不会把一句话从中间切断
   - 比固定长度分块效果好

2. **512 字符是经验最优值**
   - 太短（256）：上下文不够，检索到的 chunk 回答不了完整问题
   - 太长（1024）：一个 chunk 里混了多个主题，向量不聚焦
   - 512 字符（约 200-300 个中文词）是大多数 RAG 系统的经验值

3. **64 字符重叠（overlap）**
   - 相邻 chunk 有重叠，避免关键信息正好被切在边界上
   - overlap 太小（32）：边界信息容易丢
   - overlap 太大（128）：重复内容多，浪费向量空间
   - 64 是 512 的 12.5%，比较合理

4. **为什么不用语义分块？**
   - 太慢：每切一次都要算 embedding 相似度
   - 开发阶段不需要这么极致
   - 递归分块已经够用了，后续可以加语义分块作为高级选项

## 为什么是字符数而不是 token 数？

- 开发阶段简单：直接按字符数切，不用加载 tokenizer
- 中文场景下，字符数和 token 数大概 1:1（一个汉字约 1-2 token）
- 512 字符 ≈ 300-500 token，在 bge-m3 的 8192 token 上下文限制内

## 未来优化

- 加配置项，让用户可调 chunk_size 和 overlap
- 加语义分块作为高级选项
- 加不同分块策略的对比评估（这正是 RAGForge 要做的事）
